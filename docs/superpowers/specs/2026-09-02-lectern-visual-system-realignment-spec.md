# Lectern 视觉系统重整 Spec

## 0. 文档定位与已确认前提

本文定义 Lectern 工作台的视觉系统、布局密度和可发现性交互。它解决的不是
“再加一层皮肤”，而是让已经具备的会话、Agent、审查、预览和终端能力在第一眼
就有正确的主次。

本文依赖并不得推翻以下已定案事项：

- `2026-09-02-state-driven-workbench-ui-spec.md` 的显式
  `TaskPresentationState` 状态机表；
- 右侧第三个面板的代码与文案统一为 `preview` / “成果预览”，不再使用
  `results` / “画布”；
- `MapPane.tsx` 已删除，不重新引入地图作为常驻工作台 tab；
- `WorkbenchSelection.source = automatic | user` 契约：自动跳转不能抢走同一
  任务中用户明确选定的面板；
- Terminal resize 仅在 committed layout change 后同步，输出流、普通渲染和
  `fit()` 重排不得造成 resize 请求循环；
- 当前主结构保持为“项目内会话 | 对话 | 右侧工作区 | 底部 Debug Area”。

本文是上述状态机 spec 的视觉实施附录。功能状态由前者决定；本 spec 决定每个
状态应该如何被看见、被操作、以及在桌面空间中占多少位置。

## 1. 现状诊断

当前版本的功能骨架已经正确，但视觉上仍有六个系统性问题：

1. **同权留白。** 空闲态中对话、右侧审查和终端都留出大块区域，真正的首要
   动作“开始一个任务”反而不够突出。
2. **运行区过重。** 深色终端在空闲时占据过大的屏幕面积，像把主工作面切成
   两半；它应是需要时打开的调试区，而不是永久主角。
3. **控件语言混杂。** 黑色胶囊 tab、浅色圆角输入框、带边框的大按钮和纯文字
   工具入口并存，缺乏同一套桌面交互层级。
4. **边框多、结构弱。** 多层卡片、ring、阴影和分隔线同时出现，用户看到了
   许多边界，却难以看出当前任务、当前状态和下一步动作。
5. **任务上下文分散。** 项目、任务状态、模型、自动模式、变更和终端状态散落
   于左右工具栏与底栏，无法在一条视线中完成判断。
6. **可发现性不足。** 可拖拽分隔线、折叠控制、面板快捷键和终端范围虽然已有
   功能，但没有足够稳定的 hover、focus、tooltip 与状态反馈。

外部浏览器/桌面插件覆盖物不属于 Lectern UI，视觉验收截图前必须关闭或裁掉；
产品不应为了容纳此类覆盖物而改变布局。

## 2. 视觉方向（拍板）

### 2.1 定案：紧凑工程工作台

Lectern 采用“**浅色内容工作面 + 深色运行区 + 中性结构色**”的桌面工具方向。
它应接近成熟 IDE 和 agent harness 的信息密度与克制感，而不是：

- SaaS 仪表盘式的浮动卡片拼贴；
- 聊天产品式的大 hero、居中欢迎卡或大圆角输入框；
- 用黑色/高饱和色填满大量按钮来制造层级；
- 纯 VS Code 复刻。Lectern 仍以任务和 Agent 进展为中心，而非文件编辑器为中心。

现有 `@zmzai/theme` 中性 surface 阶梯、语义色和深浅主题机制继续使用；本期不
重换品牌色，不新引入紫色渐变、装饰性插画或纹理背景。

### 2.2 层级规则

每一屏只能有一个视觉主角：

| 任务状态 | 视觉主角 | 次要区域 | 必须降级的区域 |
| --- | --- | --- | --- |
| `idle` | 任务输入与项目上下文 | 最近会话 | Debug Area、空的审查面板 |
| `running` | 对话流和当前 Agent 操作 | 当前触及文件、运行徽标 | 非当前文件树细节 |
| `needs_input` | 等待用户操作的回复/审批块 | 任务状态条 | 自动面板跳转 |
| `review_ready` | 变更摘要与 diff | 相关文件、命令结果 | 空白预览 |
| `delivered` | 成果预览或可交付结果 | Review、继续任务输入 | 无关终端输出 |
| `failed` | 错误上下文与恢复动作 | 已产生的变更/产物 | 成功态装饰 |

右侧工作区与底部 Debug Area 不能只因“存在”就争夺主角；它们必须根据这张表
降低、收起、显示徽标或得到自动推荐。

## 3. 视觉基础令牌

### 3.1 色彩与层次

沿用 `app/globals.css` 的语义色，不在组件里散落新的十六进制色值。

| 语义 | 使用 | 禁止 |
| --- | --- | --- |
| `bg` | 应用底、主内容背景 | 用作连续卡片的描边底色 |
| `surface` | 侧栏、工作区、浮层 | 每个消息、每个工具项都包一层 surface |
| `surface-2` / `surface-3` | hover、次级条带、选中前景 | 取代成功/失败等语义色 |
| `selected` | 活跃会话、活跃文件、手动选择 | 与 `ring`、阴影、粗边框叠加制造三重选中 |
| `line` | 区域分隔与表格边界 | 给每个容器都加 border |
| `live` / `success` / `warning` / `danger` | 状态点、状态文本、极浅 tint | 做成大面积页面底色或唯一状态说明 |

深色终端继续使用独立的 VS Code Dark+ 终端配色。它是一个明确的运行时表面，
不是应用其余面板的强调色来源。

### 3.2 圆角、边框和阴影

- **结构区域**：会话栏、对话栏、工作区、Debug Area 不使用圆角；以单条
  `line` 分隔，避免“卡片套卡片”。
- **行内控件**：图标按钮、tab、输入框使用 3--4px 圆角；不得把常规工具按钮
  做成胶囊。
- **浮层**：菜单、模型选择器、对话框最大 6px 圆角，可使用一层 `line` 和一层
  小阴影。
- **状态标签**：仅用于极短状态（如“运行中”“需审批”），可为小型圆角标签；
  同一工具栏不得连续堆叠多个胶囊。
- **阴影**：只用于浮层与短暂 toast。活跃会话、tab、主输入框和各大区域不用
  阴影充当层级。

### 3.3 字体与密度

中文以现有 MiSans / PingFang 系列为主；代码、路径、命令和时间使用等宽字体。

| 文本角色 | 建议尺寸 | 规则 |
| --- | --- | --- |
| 任务标题 / 面板标题 | 13--14px | 中等字重，不使用展示级大标题 |
| 正文 / 对话 | 13--14px | 中文行高 1.55--1.65，长文本优先可读性 |
| 元数据 / 文件路径 | 11--12px | 必须满足可读对比度；不以过淡灰色隐藏真实信息 |
| 快捷键 / 计数 | 10--11px | 等宽、次级，不与主命令争抢视觉权重 |

全局 root 字号保持既有设置；组件中现有低于约 11px 的真实信息应逐项上调或移入
tooltip，不能用极小字号硬塞一行。

### 3.4 间距与高度

采用 4px 基线。以下尺寸是目标而非每处机械套用：

| 元素 | 高度/间距 |
| --- | --- |
| 顶部应用栏 | 40px |
| 任务上下文条、工作区 tab 条 | 34--36px |
| 图标按钮触达区域 | 最少 28 x 28px |
| 会话行 | 48--56px |
| 文件/终端 tab 行 | 30--32px |
| 紧凑状态 footer | 24px |
| Composer 最小高度 | 92--112px；内容增长后自然扩展 |
| 普通区域内边距 | 12px；密集表格/树可降至 8px |

## 4. 布局与状态视觉契约

### 4.1 顶部应用栏

应用栏只承载应用级信息：品牌、当前项目入口、全局导航/命令、窗口级面板控制。

- 居中的“工作台”静态文字不再占据主要视线。该空间优先提供当前任务标题或
  保持安静的窗口拖拽区域。
- 项目名不是侧栏里一段孤立小字：在任务上下文条中也可辨识当前项目/隔离副本。
- 左右工作区折叠是独立方向的图标按钮，带 tooltip 与 `aria-label`；没有两个
  含义相近、位置又相邻的方框图标。
- 鼠标悬停、键盘 focus、按下态都使用同一交互颜色阶梯，且应用栏按钮不使用
  黑色实心胶囊。

### 4.2 任务上下文条

由状态机 spec 中的 `TaskContextStrip` 实现，位于中央对话区顶部，替代散落的
“对话 / 空闲 / 自动”等独立控制。

从左到右依次呈现：任务标题与主状态、项目或 worktree、当前操作/完成摘要；
模型与权限模式放入次级元数据或菜单。运行、错误、需要输入等状态必须同时有：

1. 图标或形状；
2. 可读文字；
3. 辅助技术可读的状态说明。

宽度不足时，先折叠路径和模型，再折叠操作详情；绝不截断任务标题或只留下一个
无文字的状态点。

### 4.3 会话侧栏

- 项目切换器是侧栏的稳定起点，主项目名比绝对路径更醒目，路径为一行可截断的
  等宽次级元数据。
- “新建会话”是清楚的主要命令，但不做夸张大卡片。采用 32--36px 紧凑 command
  行；隔离副本是紧随其后的次级开关行，而不是第二个几乎同等权重的按钮。
- 会话按“需要处理 / 进行中 / 最近 / 归档”分组。这是视觉分组，不改变现有
  project-scoped session API 或归档语义。
- 活跃行采用一条左侧标记 + `selected` 背景；不要同时使用粗边框、ring、阴影和
  高饱和色。后台更新以小型可读标识提示，不替代状态文本。
- 行内的模型和提供商仅在帮助区分任务时显示；标题、状态、更新时间优先。

### 4.4 对话与 Composer

- 空闲态的中央区域应把任务输入置于视觉锚点，但不做 landing-page hero。欢迎文案
  最多两行，指向当前项目和可执行任务；不展示长教程或装饰图形。
- Composer 锚定在对话底部，宽度与消息流一致，不作为悬浮的巨大圆角卡片。
- Composer 内的模型、附件、技能、上下文用量为紧凑工具栏。常用按钮有可识别图标
  和 tooltip；发送/停止是唯一高权重动作。
- 消息文本不应被多层气泡和每条消息的卡片边框分割。工具调用、diff、权限和失败
  才使用有边界的结构块。
- `needs_input` 的一次滚动仍以权限请求消息 id 为 key；视觉强化该块，但不打断用户
  后续手动滚动。

### 4.5 右侧工作区

右侧只有三个一级 tab：**审查**、**文件**、**成果预览**。

- tab 使用低对比背景/底部 2px 指示线表达选中；移除大面积黑色填充胶囊。
- tab 的图标、文字、快捷键与计数在同一 34--36px 行内对齐。窄宽度下优先保留图标
  和 tooltip，不能把文字压成重叠的省略号。
- 审查空态必须说明当前基线和变更状态；成果预览空态说明可预览产物类型并给出
  “查看当前任务文件”的路线。两者不应只是大面积空白。
- 文件树、文件 tab、代码编辑区保持 IDE 密度。它们是结构区域，不各自套圆角卡片。
- `preview` 仍遵守自动/用户选择来源：产物生成时只推荐或自动选择一次，用户已在
  审查/文件时不强行切走。

### 4.6 Debug Area

Debug Area 是底部跨越中央与右侧列的运行时区域，Phase 1 只提供真实的 Terminal。

- 新建空闲任务默认收起；对同一项目用户显式打开过，或存在活动进程/未读错误时，
  保留其选择。`Cmd/Ctrl+J` 永远可切换。
- 打开时采用 30--32px 紧凑 tab 行：终端名称、运行状态、关闭、+ 新建、分屏、
  shell/更多菜单。不可用动作不展示伪按钮。
- 黑色内容区不加额外圆角、白卡或大幅说明文本。空终端应立即可输入；无 PTY 时
  才在行内明确说明降级能力。
- 活动、失败和未读输出用小徽标显示于 Debug Area tab/底栏，不因为每一条输出而
  反复展开、抢焦点或触发尺寸同步。
- “Problems / Output / Debug Console”只在存在真实数据与行为时加入 tab。禁止以
  空 placeholder 伪造完整 IDE。

### 4.7 分隔线、折叠与状态栏

- 三条 splitter（左侧、右侧、底部）均使用 8px pointer hit target，视觉轨道平时
  为透明或极弱；hover、drag、focus 时显示 `line-strong`/选中态与 resize cursor。
- splitter 双击恢复默认尺寸；焦点状态可用方向键、Home、End 操作，语义仍为
  `role="separator"`。
- 右侧工作区和 Debug Area 的收起按钮分别表达方向、目标和快捷键。收起一个区域
  不改变其他区域的开关/尺寸。
- 底部状态栏只容纳活动状态、连接/模型等短元数据和终端开关。它不是第二个工具栏，
  不重复顶部/上下文条已有信息。

## 5. 组件落地边界

本期不引入一个通用“大设计系统”或新的 UI library。现有 Tailwind +
`@zmzai/theme` 保持不变；只把已经跨组件重复的工作台模式抽成语义化、可复用的
小组件或 class recipe。

| 文件/模块 | 改动责任 |
| --- | --- |
| `app/globals.css` | 补充工作台布局、focus、splitter、tab 与空态的语义 class；只使用现有主题令牌。 |
| `lib/task-presentation.ts` | 沿用已定状态机，产出视觉所需的 state label、icon kind、priority 与 badge model；不写 JSX。 |
| `components/TaskContextStrip.tsx` | 渲染任务标题、状态、项目/worktree、摘要和次级元数据。 |
| `app/page.tsx` | 负责将派生状态、布局开关与当前会话传给区域；保留为编排层，不积累样式判断。 |
| `components/SessionList.tsx` | 以已派生的分组与状态展示会话；降低模型/提供商的视觉权重。 |
| `components/ChatView.tsx` | 清理固定 header 中重复的状态 pill；统一消息、工具块、审批块的密度与边界。 |
| `components/Composer.tsx` | 重做为底部任务编辑器：紧凑、锚定、明确主提交/停止动作。 |
| `components/WorkbenchPanel.tsx` | 将一级 tab 改为 underline 风格，落实 automatic/user 的选择来源；移除遗留“画布/地图”注释。 |
| `components/ReviewPane.tsx` | 增加任务变更摘要与可读空态；避免 card 套 card。 |
| `components/CanvasPane.tsx` | 保持组件名以避免无谓重命名，但 UI 统一称“成果预览”；提供结果来源和紧凑工具栏。 |
| `components/TerminalPane.tsx` | 只负责 xterm 与终端会话内容；其 tab chrome 移入 `DebugArea` 后仍不改变 PTY ownership。 |
| `components/DebugArea.tsx` | 新增 Phase 1 包装层，承载 terminal tab 行、徽标、collapse/focus 命令与未来 debug tab 注册点。 |

命名注意：`CanvasPane` 是内部实现名，用户可见文案一律为“成果预览”。不要为视觉
重整重引入 `MapPane`，也不要在注释、aria label 或快捷键中遗留“画布 / 地图”。

## 6. 实施顺序

### Phase V0：视觉基础与可发现性

1. 建立工作台 shell、tab、icon button、empty state、splitter 的语义 class recipe。
2. 统一圆角、边框、阴影、字体最小尺寸，移除结构区的卡片化叠层与一级 tab 的黑色
   胶囊样式。
3. 改造 splitter 的 hover/focus/drag/reset 反馈和 tooltip，不改变其既有尺寸约束。
4. 收紧顶部应用栏、会话栏、tab 行、footer 的高度；清理重复状态信息。

**完成门槛：** 不改变 session/terminal/workbench 业务行为的前提下，空闲、运行、
审查三个截图的层级和控件语言已经一致。

### Phase V1：状态机的视觉映射

1. 按既有 spec 实现 `deriveTaskPresentation` 及其单测。
2. 实现 `TaskContextStrip`，以显式状态机作为唯一状态展示来源。
3. 将 SessionList 分为需要处理、进行中、最近、归档，并落地不依赖颜色的状态行。
4. 按 automatic/user 契约让 Review、Files、Preview 获得推荐而不抢选中。
5. 为 `needs_input`、`failed`、`review_ready`、`delivered` 分别实现有动作的空/结果态。

**完成门槛：** 同一任务从运行到产物生成、再到用户审查，面板可以主动推荐但不会
抢走用户已选的区域；状态文案不再散落在三个工具栏。

### Phase V2：Debug Area 收敛

1. 将 `TerminalPane` 放入 `DebugArea`，先只提供 Terminal 一项。
2. 重整终端 tab 行、活动/错误徽标、focus 行为和 `Cmd/Ctrl+J`。
3. 空闲新任务默认关闭 Debug Area；活动进程与用户偏好按既有规则保留。
4. 完成独立 terminal resize 闭环测试后才允许合并。

**完成门槛：** 终端在需要时达到 VS Code 式可用密度，在空闲时不压迫主任务；打开、
关闭、拖拽、输出和普通重渲染均不会产生 resize 刷屏。

### Phase V3：审查与交付细节

1. 审查页加入任务内变更摘要、命令/测试结果行和可读的无变更状态。
2. 成果预览显示来源文件、viewport、刷新和打开动作；可交付但不可预览的结果显示
   文件/命令/URL outcome row。
3. 仅当 structured diagnostics 有真实上游数据后，再加 Problems / Output；Debug
   Console 等待实际 debugger 协议。

## 7. 视觉验收清单

### 7.1 桌面截图矩阵

在相同主题下，至少验证 1440 x 900、1728 x 1117 与 1180px 临界宽度：

| 场景 | 必验视觉结果 |
| --- | --- |
| 新空闲任务 | Composer 是中央锚点；Debug Area 收起；右侧不留无解释的大空白。 |
| 运行中文件任务 | 状态条、当前操作、对话流和文件推荐清晰；终端不抢焦点。 |
| 待审批 | 审批块和任务状态在一次视线范围内；右/下区域保持用户选择。 |
| 有变更待审查 | Review 有摘要、相关文件和明确 baseline；tab 不用黑色胶囊。 |
| 有 HTML 产物 | Preview 是自动推荐结果；手动固定在 Files/Review 时不跳走。 |
| 失败但仍有产物 | 产物可见，失败作为次级信息可追溯。 |
| 打开 Terminal | 终端与 tab 行可用、密集、无多余空态文案；`Cmd/Ctrl+J` 可关回。 |

### 7.2 交互与可访问性

- 所有图标按钮有 `title`、`aria-label`、28px 以上可点击区域和可见 focus ring。
- 任意 tab、会话、splitter 只用键盘也可聚焦并理解状态；颜色不是唯一表达。
- 文本无重叠、截断造成的歧义或因缩放而跳动的布局。
- 所有 splitter 在 hover、focus、drag 中有不同但克制的视觉反馈；双击可复位。
- `Cmd/Ctrl+J`、`Cmd/Ctrl+\``、`Cmd/Ctrl+B` 和 workbench 快捷键经过 Electron
  `before-input-event` 冲突自查；与系统/终端冲突时降级为命令面板入口。

### 7.3 技术质量门禁

- 样式改动不得写入硬编码主题色；深浅主题的新增样式使用既有 semantic token。
- 运行 `pnpm typecheck` 与组件/状态机测试。
- Playwright 对上述截图矩阵进行截图与 overflow 检查；至少人工检查一次 Electron
  真窗口的 title bar、focus ring、终端字体和拖拽区。
- 记录 `/api/terminal/:id/resize` 请求：一次 committed layout change 最多产生一次
  合法同步；SSE 输出、轮询替换、消息流增量和普通 React render 产生零次请求。
- 切换两个隔离项目/会话后，页面不得残留前一个任务的状态条、preview、Review、
  终端标识或选择高亮。

## 8. 非目标与守则

- 不以视觉重整为名重写已稳定的会话隔离、文件根目录、git 或 PTY 后端。
- 不在没有真实数据时发布 Problems、Output、Debug Console 的空 tab。
- 不将状态机逻辑藏在 CSS class 判断或各组件的局部 `useEffect` 中；视觉组件只消费
  `lib/task-presentation.ts` 的派生模型。
- 不增加营销语言、功能说明墙、渐变背景、装饰性插画或大英雄标题。
- 不保留已下线面板的 import、注释、快捷键、tooltip 或空组件；每个删除必须全仓
  搜索验证。

## 9. 交付定义

视觉系统重整完成不等于“界面更白、更圆或更像某个产品”。完成的定义是：

1. 用户可以在一眼内认出当前项目、任务状态和下一步；
2. 当前任务状态决定视觉主角，用户明确的面板选择永远优先；
3. 空闲、执行、审查、交付、失败五类页面都没有不解释的大面积空白或永久抢戏的
   终端；
4. 控件、tab、边框、字体、间距和 focus 反馈是一套一致的紧凑桌面语言；
5. 所有视觉改善在隔离会话、真实终端、快捷键和 resize 门禁下仍然可靠。
